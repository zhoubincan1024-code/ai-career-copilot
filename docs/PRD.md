## 二、产品概述

### 2.1 背景与问题

- 2026 届毕业生 1270 万，本科生平均投 **46 份简历**才获得 1 次面试，求职周期拉长到 3.5 个月
- 超 60% 企业使用 ATS 机器初筛简历，双非学生简历通过率低至 13.5%
- 核心痛点：投递无回音、简历与 JD 不匹配、定位模糊、面试紧张不会复盘（详见用户研究）

### 2.2 一句话定位

> **面向中国应届生的、以"可解释匹配 + 数据复盘"为核心的 AI 求职决策与面试助手。**

### 2.3 产品目标

| 维度 | 目标 |
|---|---|
| 用户价值 | 让求职者"知道该投什么、简历差在哪、面试怎么练、复盘怎么做" |
| 北极星指标 | **每周完成一次"有效求职决策"的用户数**（有效求职决策 = 完成简历上传 + 岗位匹配并查看 Gap 建议） |
| 作品集目标 | 完整证明"需求发现 → 产品设计 → AI 实现 → 评测 → 数据迭代"的闭环能力 |

### 2.4 成功标准（MVP 版）

1. 用户能上传/输入简历与 JD，并获得稳定的结构化结果（JSON 可解析率 >99%）
2. 岗位匹配结果可解释（不是只有百分比，而是强项/短板/Gap/建议）
3. RAG 回答有来源引用，检索不到时不编造
4. AI 面试能连续追问并生成结构化评分
5. 投递数据可复盘（漏斗可视化）
6. 具备一套 ≥50 条的 Evaluation 测试集

## 四、核心用户流程

### 4.1 端到端主流程

```
注册/登录
   ↓
上传简历（PDF/文本）→ 简历结构化解析
   ↓
填写目标岗位 或 上传/粘贴 JD → JD 结构化解析
   ↓
岗位匹配（Match Analyzer）
   ├─ 匹配总分 + 维度分（技能/经验/教育/表达）
   ├─ 优势
   ├─ Gap（差距项清单）
   └─ 行动建议
   ↓
选择分支：
   ├─ 简历优化 → 逐段改写 + 修改理由 → 接受/拒绝
   ├─ AI 模拟面试 → 连续追问 → 结构化评分 + 复盘
   └─ RAG 知识库 → 检索问答 → 带引用回答
   ↓
记录投递（岗位/状态/时间）
   ↓
Dashboard 数据复盘（漏斗/来源/面试表现）
   ↓
AI 生成下一步行动建议
```

### 4.2 关键场景拆解

**场景 1：简历诊断（激活路径）**
用户上传简历 → 系统结构化解析 → 给出"你的简历画像"（技能/经历/亮点）→ 引导下一步：填目标岗位做匹配。

**场景 2：岗位匹配与 Gap 分析（核心价值）**
用户粘贴目标 JD → 系统解析 JD 要求 → 与简历对比 → 输出匹配总分、各维度分、Gap 清单、行动建议 → 一键进入"简历优化"。

**场景 3：AI 面试训练（高频留存）**
选择目标岗位 → AI 模拟面试官按 JD 出题 → 用户回答 → 追问 → 结束出报告（能力评分 + 反馈 + 改进建议）。

**场景 4：投递复盘（数据闭环）**
记录每次投递状态 → 漏斗展示 投递→面试→Offer → 结合面试复盘数据给出下阶段建议。

- 不做招聘信息聚合/爬虫（合规与成本高）

- 不做实时面试作弊辅助（伦理问题）
- 不做多语言/海外求职（聚焦中国市场）
- 不做移动端原生 App（Web 优先，验证后再说）

## 六、P0 功能详述

### 6.1 Dashboard（首页）

| 项 | 说明 |
|---|---|
| 目标 | 一屏掌握求职全局，给出下一步行动 |
| 区块 | ① 匹配度总览 ② 投递漏斗（简版）③ 近期岗位 ④ AI 行动建议 |
| 交互 | 点击卡片进入对应详情页 |
| 空状态 | 未上传简历时引导上传；未匹配时引导填写目标岗位 |

### 6.2 简历管理

- 支持上传 PDF / 粘贴文本
- 结构化解析输出：教育、技能、项目经历、工作经历、亮点
- 版本管理：一次上传一版本，可回看历史版本（v1/v2/v3）
- 解析失败时提示用户重传/补充文本

### 6.3 JD 分析

- 支持粘贴 JD 文本（MVP 不做自动抓取）
- 结构化输出：岗位名称、职责、硬性技能、软性技能、经验年限、关键词
- 展示"招聘意图解读"（该岗位真正看重什么）

### 6.4 岗位匹配（核心差异点）

- 输入：简历 JSON + JD JSON
- 输出：匹配总分、维度分（技能/经验/教育/表达）、优势清单、Gap 清单、行动建议
- **可解释性要求**：每一条结论必须给出依据（对应简历哪条经历 / JD 哪条要求），不允许只给百分比

### 6.5 简历优化

- 输入：简历原文 + 目标 JD
- 输出：逐段优化稿 + 修改理由（为什么这么改、对应 JD 哪条）
- 交互：接受/拒绝每处修改，拒绝后可手动编辑
- 原则：基于真实经历改写，不编造经历（对齐竞品"鹅来面"的价值观）

### 6.6 AI 模拟面试

- 选择岗位 → AI 按 JD + 简历出题（含 1 分钟自我介绍、项目深挖、行为问题）
- 支持连续追问（对含糊回答继续深挖）
- 结束生成：能力评分（专业知识/表达/逻辑/匹配度）+ 逐题反馈 + 改进建议
- 面试记录保存，可供复盘

## 七、P1/P2 功能概述

### 7.1 RAG 知识库（P1）

- 上传求职资料（PDF/Markdown/文本）→ 解析 → 切分（500~800 tokens）→ Embedding → pgvector
- 检索问答：Query → Top-K 检索 → 构造 Context → LLM 回答 + 来源引用
- 首批内置内容：AI 产品面试题、PRD 方法、AI 产品案例、RAG/Agent 基础、产品指标
- 检索不到时必须明示"未找到相关资料"，不编造

### 7.2 投递管理（P1）

- 记录：公司、岗位、投递日期、状态（已投/笔试/面试/Offer/被拒）、备注
- 列表 + 看板视图

### 7.3 数据分析（P1）

- 漏斗：投递 → 面试 → Offer 转化
- 维度：时间范围、岗位类型、来源渠道
- 行为：岗位分析次数、简历优化次数、面试完成率

### 7.4 AI 规划（P2）

- 输入目标岗位 → 输出学习/求职周计划
- 依赖：RAG 知识库沉淀 + 用户行为数据

## 八、产品指标设计

### 8.1 指标框架

| 层级 | 指标 | 定义 |
|---|---|---|
| **北极星** | 有效求职决策用户数/周 | 完成"上传简历 + 完成岗位匹配并查看 Gap 建议"的用户数/周 |
| 激活 | 完成率 | 完成"简历上传 + 首次岗位匹配" |
| 核心行为 | 使用频次 | 岗位分析次数、简历优化次数、面试完成率（面试完成/面试开始） |
| 转化 | 漏斗转化 | 匹配→投递、投递→面试、面试→Offer |
| 留存 | 留存率 | D1/D7 留存 |
| AI 质量 | 质量指标 | 准确率、幻觉率、满意度（详见 Evaluation） |
| 成本 | 成本指标 | 每活跃用户 Token 成本、单次任务成本 |

### 8.2 北极星指标说明

- 为什么选"有效求职决策"而非"注册数"：注册不代表价值，**完成一次有意义的求职动作**才证明产品价值
- 它同时驱动：激活（上传+匹配）、留存（每周回来做决策）、变现潜力（求职决策的后续行为）

### 8.3 关键事件埋点清单（MVP）

| 事件名 | 触发时机 | 参数 |
|---|---|---|
| resume_uploaded | 简历上传成功 | user_id, parse_status, parse_ms |
| resume_parsed | 解析完成 | json_valid, fields_count |
| jd_uploaded | JD 提交成功 | user_id, job_title |
| match_generated | 匹配完成 | match_score, gap_count |
| match_detail_viewed | 查看匹配详情 | score, dimension |
| resume_optimized | 完成一次简历优化 | edit_accepted_count, edit_rejected_count |
| interview_started | 开始模拟面试 | job_id |
| interview_completed | 完成面试 | question_count, score |
| application_created | 记录投递 | job_id, status |
| rag_question_asked | 知识库提问 | has_citation, retrieval_count |

### 8.4 埋点原则

- 事件命名统一 `对象_动作` 风格
- 关键漏斗事件必须前后端一致（以服务端为准）
- MVP 先保证"漏斗 5 事件 + 北极星 1 事件"能完整统计

## 九、AI 能力与理由

| 功能点 | AI 技术 | 为什么用它 |
|---|---|---|
| JD/简历解析 | LLM + Structured Output | 非结构化文本 → 稳定 JSON，替代规则引擎（关键词抽取复杂多变） |
| 岗位匹配 | LLM + 规则加权 | LLM 理解语义匹配，规则保证分数可解释、可复算 |
| 简历优化 | LLM + Prompt 版本管理 | 生成式改写，每版 Prompt 可评测迭代 |
| 模拟面试 | LLM 多轮对话 + 评测 Prompt | 动态追问需理解上下文 |
| 知识库问答 | RAG（Embedding + pgvector） | 领域知识要"引用来源、可溯源"，纯 LLM 无法保证 |
| 效果评测 | Evaluation 测试集 | 用数据证明质量，驱动 Prompt/模型迭代 |

> 原则：不堆技术名词。每一项 AI 能力都必须能回答"为什么不用别的方式"。

## 十、非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 单次 AI 任务平均延迟 <4s；解析类 <5s |
| 可用性 | MVP 可用性目标 99%（本地 Demo 阶段 95% 即可） |
| 安全 | 用户数据加密存储；简历/JD 数据仅本人可见；API Key 服务端保存 |
| 隐私 | 明确告知数据用途；支持删除用户数据 |
| 可维护 | 前后端分离；Prompt 进版本管理；文档与代码同等重要 |

| 版本 | 范围 | 里程碑 |

## 十二、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 输出不稳定 | 解析/匹配质量波动 | Structured Output + JSON 校验 + Evaluation 测试集兜底 |
| 简历隐私担忧 | 用户不敢上传 | 数据加密、仅本人可见、提供删除功能、Demo 说明 |
| 匹配结果不可解释 | 用户不信任 | 强制"结论带依据"，Gap 必须能溯源到 JD/简历 |
| RAG 检索质量差 | 回答不相关 | 从 500~800 tokens 切分起步，用 Recall@K 评测迭代 |
| 时间不足做不完 | 半成品 | 严守 MVP 边界，砍 P2，宁可做深一个模块 |
| 面试讲不清 | 作品浪费 | 文档（PRD/用户研究）+ 演示视频 + 5~10 分钟故事线（见 README） |

## 十三、附录

### 13.1 术语表

| 术语 | 含义 |
|---|---|
| ATS | Applicant Tracking System，招聘管理系统，会做简历关键词初筛 |

| pgvector | PostgreSQL 的向量检索扩展，用于语义检索 |
| Faithfulness | 回答是否被检索上下文支撑的程度 |
